# アクセサリ構想メモ（対象セレクタ統合と対応形式の拡張）

## 発端

下パネルのアクセサリ欄が邪魔である。現状、対象セレクタが2箇所にある。左のモデル／カメラ用セレクタと、アクセサリ欄が持つ独自のセレクタである。「いま何を編集しているか」の答えが画面に2つある。

## 結論（方針）

アクセサリをモデルと同じ扱いにし、**カメラ / モデル / アクセサリ を1つの対象セレクタに並べる。**

### 判断の根拠

分類の基準は座標の有無ではなく、**単数か複数か**とする。

|          | 個数 | 置き場所            |
| -------- | -- | --------------- |
| 照明（平行光源） | 1個 | 下パネル            |
| セルフ影     | 1個 | 下パネル            |
| 重力       | 1個 | 下パネル            |
| カメラ      | 1個 | 対象セレクタ（編集対象のため） |
| モデル      | N個 | 対象セレクタ          |
| アクセサリ    | N個 | 対象セレクタ          |

現状の下パネルは、1個ずつのものが並ぶ棚に、N個あるものが1つだけ混ざっている。そのため中に小さなセレクタを持たされ、それが対象セレクタの二重化を生んでいる。**席替えではなく分類の修正である。**

なお本家MMDのタイムラインでは、カメラ・照明・セルフ影・重力が上部に固まり、アクセサリは別枠で下に積まれる。**タイムライン側は既に単数と複数を分けている。下パネルだけが混ざっている。**

### 得られるもの

1. 対象セレクタが1本になる。
2. **カメラモードの下パネルからアクセサリ欄が抜け、重力欄を入れられる。** 重力は 加速度 / ノイズ / 方向XYZ 程度で、照明欄とほぼ同規模のため収まる見込み。
3. クローズアップ表示の単位ルール（選択したものが属する単位を開く）が、アクセサリにもそのまま適用できる。アクセサリは XYZ / RxRyRz / Si / Tr の8チャンネルで、ボーンやカメラと同程度の密度になる。

### 副次的な候補：タイムラインのモード切り替えを廃せる

対象セレクタが1本なら、タイムラインのモード（モデル編 / カメラ・照明・アクセサリ編）は**選択から導出できる**。モデルを選べばボーン・モーフのタイムライン、カメラやアクセサリを選べばそちらになる。

コントロールが1つ減り、「モードを切り替え忘れてキーが見つからない」が構造的に起きなくなる。操作体系は互換の対象外であるため、本家と変えてよい領域である。

## アクセサリの定義を広げる

**アクセサリ = 何か置くもの**とする。メッシュを持つとは限らない。

| 種類                              | 持つもの              |
| ------------------------------- | ----------------- |
| PMX / .x アクセサリ                  | メッシュ、材質           |
| OBJ / PLY                       | メッシュ、材質または頂点色（静的） |
| PNG / 連番PNG / GIF / APNG / WebP | 板、テクスチャ、時間軸       |
| 点光源（候補）                         | 色、強度、範囲。メッシュなし    |
| ボリューム系（候補）                      | 範囲。メッシュなし         |

こう定義すると、位置・回転・キー打ち・外部親が全種類でそのまま使える。点光源をキャラの手に外部親で付ける、といったことが追加実装なしで成立する。

### パネルは拡張子で分岐させない

`.ply なら頂点色欄を出す` のように書くと、形式が増えるたびにパネルを触ることになる。**ローダーが自分の能力を申告し、パネルはその申告から生やす。**

- 材質を持つか
- 頂点色を持つか
- スケールは単一値か軸別か
- 時間軸を持つか
- テクスチャを持つか

PMX の表情パネル分類をそのまま使うのと同じ方針である。名前や拡張子で推測せず、読み込んだものが持っている情報を使う。

### 下パネルに入れるもの

アクセサリ選択時の下パネルには、スケールなど**各形式の固有機能**を入れる。時間軸を持つものには、開始オフセット・リピート速度・ループ方法を置く。

板ポリ系には次が要る。これらを欠くとスプライトが「シール」に見える。

- **ビルボード**（常にカメラを向く）
- **合成モード**（通常 / 加算 / 乗算）— 炎や光は加算でないと発光して見えない
- **ライティングを受けるか**（自己発光扱いにできるか）
- **深度書き込み**（複数枚重ねたときの順序破綻を避ける）

これらは板ポリ系アクセサリ全般で使えるため、特定形式専用の機能にはならない。

## 対応形式について

### OBJ / PLY

fbx や glTF はシーングラフ・スキン・アニメーション・モーフを持つため、静的として読むと**ファイルが宣言しているものを黙って落とす**ことになる。対して OBJ / PLY はそもそも静的な形状しか持たないため、**静的として読むことが完全対応になる。**

実装難易度も重くない見込み。Babylon.js がローダーを持っており、全て自前ではない。

難所はパースではなく、軸と単位の変換（MMD は Y-up の独自スケール、Blender 出力の OBJ は Z-up）、および材質の扱い（MTL にトゥーンの概念がない）。ここは実物を入れてから決める。

PLY の注意点として、PLY は任意のプロパティを宣言できる器であり、ascii と binary の両方が来る。方針は「x/y/z と面を読む、色と法線があれば使う、**知らないプロパティは読み飛ばす**」とする。**面を持たない PLY（点群）をどう扱うかは要決定。**無言で何も表示されない状態にはしない。

### 画像・動画

PNG は板に貼るだけで済むため早い。GIF は中身がフレーム列で各フレームに表示時間が埋まっているため、**動画の同期問題が原理的に起きない。**連番PNGを1ファイルにまとめたものと考えてよい。

ただし **GIF の透過は1bit** であり、炎や煙のような柔らかい縁のものは汚くなる。フルアルファが要る用途では連番PNG / APNG / アニメーションWebP を使う。

**動画は本質的な難所が別にある。**「再生」ではなく「タイムラインに従属させる」ことである。フレーム1014を表示しているとき動画の該当時刻の絵が出ている必要があり、スクラブにも追従し、書き出し時にはフレーム精度で取り出せなければならない。HTML の video 要素はフレーム精度のシークができない。

**したがって連番PNGを先に実装する。**フレーム N がファイル N に対応するため同期問題が存在せず、動画対応の価値の大部分を小さいコストで得られる。時間軸・リピート速度のパネル設計も、連番PNGの時点で固まる。動画の直読みはその後で検討する。

## やらないこと

- **パーティクルシステム。** 発生数・寿命・初速・減衰に踏み込まない。線は「1枚の板に絵を貼り、合成方法を選べるところまで」。それ以上は外部WGSLシェーダの経路が担当する。
- **fbx / glTF の部分対応。** 落とすものがある形式を「静的として読める」とは言わない。
- **ビューアを別プロダクトにしない。** 3Dビューアとしての用途は同じアプリの軽い入口として持つ。保守対象を2つにしない。モードであってプロダクトではない。

## 未決定事項

- 点光源やボリューム系を「アクセサリの一種」として扱うか、新しいカテゴリを立てるか
- 点光源などは本家MMDに存在しない独自機能である。AGENTS.md の「実験機能は設定・機能フラグ・分離された導線のいずれかで隔離する」とどう折り合いを付けるか。対象セレクタに並べる場合は**隔離しない**という判断になる。意識して決めた記録を残す
- アクセサリ欄を外した後、下パネルが余る扱い。全モードが同じ密度である必要はないため、空けたまま出して様子を見る案もある。埋めるなら材質欄が本命（アクセサリで使いたくなる筆頭であり、OBJ を読むなら必須になる）
- 対象セレクタにアクセサリが多数並んだときの見つけにくさ（見出しでグループ分けするか）
- 選択の型によって下パネルのレイアウトごと差し替わる構造をどう持つか
- 面を持たない PLY の扱い（点群として描くか、明示的に非対応と伝えるか）
- 軸・単位変換の指定UI

## 順序

この構想は VMD 出力・カメラ外部親より後である。ただし対象セレクタの統合だけは、**重力欄の置き場所を作るという実利がある**ため、照明・影・重力のキー打ち対応に着手する時点で必要になる可能性がある。
