# アリシアのダンス再生でのRC GI・天空遮蔽の軽量化

2026-11-03。所有者が指定したローカルリファレンスのアリシアと同梱VMDを実際に読み込み、ダンスの通常再生で比較した。実機の重いプロジェクトでは前回、FrameGraph全体OFFが60 FPS、天空遮蔽のみ20 FPS、GIのみ19 FPS、併用13 FPSだった。[前回の実機結果と自作シーンでの切り分け](./rc-playback-performance-2026-11-03.md)

## 検証シーン

- `Alicia_solid.pmx` に、ファイルメニューから `2分ループステップ20.vmd` を読み込む。アリシアは22メッシュ、22,311頂点、31,866三角形。床18,432三角形と反射色・遮蔽を確認する自作の36三角形を置き、各効果に入力された不透明な面の合計は42,912三角形だった。モデルとモーションは [リファレンス台帳](./test-reference-asset-ledger.md) を参照。
- Windows、Electron 40.4.1、Babylon.js 9.2.0、NVIDIA AmpereのWebGPU。1280×720、カメラ・照明・計算範囲を固定し、物理と通常の影をOFFにした。各条件で別のElectronを起動し、再生ボタンからVMDを再生する。12フレームのウォームアップ後に80フレームを計測。FPSは平均フレーム間隔の逆数、CPU・GPUの内訳は中央値。
- 比較元のRC実装は `df27f5d`。同じ計測コードと同じローカル素材を変更前後で使った。FPSは時間ベースの通常再生で測り、画質は毎回同じフレームにシークして比較した。

## 実装

姿勢だけが変わるときは、三角形のXYZを読み出して遮蔽判定用のBVHへ転記するループで、そのまま葉の境界を求める。集約BVHには変わった境界を反映する。メッシュの順番・数・三角形数が変わった場合は走査順と三角形IDを組み直す。発光材質を囲う範囲はルミナスが必要とした時に計算し、複数材質で同じUVチャンネルを使うメッシュではその入力を一度だけ照合する。

GPU上では各格子点の近くにある2枚の三角形を調べ、照明を材質に適用するときの面の突き抜けを抑えている。この探索が届く距離は格子間隔の√3倍なので、変更前後のメッシュ境界を2格子分広げ、その外側の格子点は前回の結果を使う。計算範囲・三角形IDの変更、初回、複数回の形状更新を取り逃した場合は全域を更新する。カスケードの照明自体はキャラが動いたフレームごとに計算する。

変更範囲内では、前フレームの候補2枚が現在のポーズで格子点からどれだけ離れたかを測る。異なる有効な2枚があれば、そのうち遠い方の距離は、2番目に近い面までの距離の上限になる。この上限に丸め誤差用の余裕を足して探索を始め、通常の順番で最終候補を選ぶ。有効な2枚が揃わなければ元の半径を使う。候補IDを保持するGPUバッファは16³格子で各32 KiB、両効果で64 KiB。CPUへの読み戻しは検証時だけ行う。

## 計測結果

| 効果 | 平均FPS（前 → 後） | CPU形状更新（ms） | GPUパス合計（ms） |
| --- | ---: | ---: | ---: |
| 両方OFF | 59.3 → 59.3 | 0 → 0 | 0.38 → 0.38 |
| GIのみ | 50.3 → 55.8 | 7.63 → 6.49 | 3.77 → 2.43 |
| 天空遮蔽のみ | 51.3 → 56.3 | 7.29 → 6.07 | 3.99 → 2.67 |
| 両方ON | 39.0 → 43.0 | 12.64 → 10.63 | 6.74 → 4.87 |

併用時のフレーム間隔の95パーセンタイルは34.50 → 30.16 ms。CPU形状更新のうちBVH更新が4.60 → 3.85 ms。GPUの近傍探索は天空遮蔽が1.74 → 0.65 ms、GIが1.74 → 0.59 msだった。CPUとGPUは動作が重なるため個別時間を足してフレーム時間を推定しない。両方ONを別プロセスでもう一度測ると41.45 FPS、95パーセンタイル32.79 ms、CPU形状更新10.78 ms、GPUパス合計4.94 msだった。

三角形・BVH等のGPU転送要求量は併用で前後とも5,650,080 B/フレーム。転送要求を提出するCPU時間は変更前に0.48 msだった。今回は転送レイアウトを保ち、CPUでの形状準備とGPUでの探索時間を短縮した。

### 所有者のダンスプロジェクトでの再確認

RC GIと天空遮蔽を併用した再生で、所有者が確認したFPS表示は **13 → 14 FPS**。表示値からの換算では約76.9 → 71.4 ms/フレームで、今回の短縮幅は約5.5 msに相当する。

同日の開発版ログ `main-dev.log` に、5モデル・Bullet MPR・再生中の性能サンプルが残っていた。18:21:38の14 FPS区間（直近10秒、138フレーム）では、CPU側で測ったフレーム全体が平均68.43 ms、うち `activeMeshesEvaluation` が51.71 ms、後段の `postEffectBackend` が0.64 ms。物理ステップは平均4.38 msだった。前回の全体OFFのスクリーンショットに近い14:22:27のログでは、60 FPSで `activeMeshesEvaluation` が0.40 ms（600フレーム）。撮影区間は異なる。

このメッシュ評価区間には、カメラ描画前に実行するRC天空遮蔽とRC GIの `prepareFrame()` の両方が含まれる。実機で時間が増える区間はここまで絞れる。個別のRC形状更新・転送要求・GPUパス時間を記録したのは、この文書のアリシア比較用プローブである。

### 姿勢更新時の中間コピー削減

姿勢だけが変わった場合、共有済みのワールド頂点と、対象面の頂点インデックスを使って、既存のソート済みBVHへ座標を直接書き込むようにした。以前の「24 float/三角形のレコードを複製 → 元の順番でXYZを詰め直す → BVH順へ再転記」の最初の2段階を省く。三角形の順番、材質色、UV、境界の余裕幅、GPU入力形式は維持する。参照先の座標を検査してから入力を公開し、不正な座標では既存の拒否経路で照明をクリアする。

材質用レコードは不変のまま、最新の位置を別に保持する。RGBだけの変更でも最新位置を保持し、発光範囲もその位置から求める。非表示からの復帰などで新しいBVHが必要な場合は、最新位置を完全なレコードに戻して構築する。各効果は独立したBVH順序を保持するため、別のポーズで有効にした効果の三角形IDを混在させない。

アリシアの同じシーン・設定で、各回を別プロセスにして比較した。両側ともCPUプロファイル取得を先に終え、12フレームのウォームアップ後の80フレームを通常の計時プローブで測った。通常影と物理はOFF、解像度1280×720。計算頻度・照明設定の変更はない。

| 項目 | 変更前 | 変更後 | 別プロセスで再測定 |
| --- | ---: | ---: | ---: |
| 平均FPS | 44.1 | 53.7 | 54.0 |
| CPU形状準備 中央値ms | 10.93 | 8.36 | 8.30 |
| うちBVH更新 中央値ms | 4.06 | 3.69 | 3.70 |
| CPUフレーム全体 中央値ms | 18.80 | 15.92 | 15.81 |
| フレーム間隔95パーセンタイルms | 29.10 | 20.26 | 19.95 |

形状準備は約24%短縮。転送要求量は前後とも5,650,080 B/フレーム、カスケード等のdispatch数も同じ。V8のサンプルでも、ソース更新本体と新しい位置検査を合わせた割合は、ソース内の29.2%から7.1%へ減った。速くなった分だけ同じ秒数に処理するフレームが増えるため、プロファイルの絶対サンプル時間をフレーム当たりの時間と取り違えない。

0 → 60 → 0フレームのPNG3枚と、両効果の近傍面atlas6個は、変更前との2回の比較ですべてバイト一致。GIの照明・色・形状変更、天空遮蔽の無効化と復帰、GUIからの骨・モーフの直シーク、ルミナスの発光UV、不透明PNGのX室内の回帰E2E5件も成功し、WebGPU検証エラーは0件だった。

物理と通常影をONにした別の通常ログE2Eも成功。再生中10秒・600フレームのメッシュ評価平均8.773 msは、天空遮蔽準備5.407 ms、GI準備3.236 ms、その他0.130 msに分解でき、FPS表示は60だった。これは計時プローブを付けた上表とも、所有者の重いプロジェクトとも条件が異なる。所有者プロジェクトの修正後FPSは再確認待ち。

## 画質・回帰確認

以下は11月3日の最適化時の確認結果。

4条件で0 → 60 → 0フレームに直接シークし、1280×720のPNG計12枚が変更前と一致した。両効果の格子点4,096個が保持する近傍面のIDと有効フラグも、RGBA32Fの生データ計12個がバイト単位で一致した。全条件でWebGPU検証エラー0件。

GIの照明・反射色・形状変更、天空遮蔽の無効化・復帰、骨とモーフの直シーク、ルミナスの発光テクスチャUV、不透明PNGを使うX室内の既存5ケースに成功。以前の51,236三角形の自作シーンでも併用時のPNG3枚が一致し、前回の44.2 FPSに対して今回48.2 FPSだった。全単体テスト1,450件とlintが通過した。型検査は既存547件、変更ファイルの型エラーと未定義名のcriticalエラーは0件。
