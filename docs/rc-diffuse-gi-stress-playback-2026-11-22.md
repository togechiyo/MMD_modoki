# GI RCの高負荷連続再生テスト

## フルHDでの結果

90,112三角形のうち65,536三角形が動くシーンでは、通常再生はGIオフで60.0 FPS、1バウンスで59.1 FPS、2バウンスで57.6 FPSだった。モデルを3つに増やすと、どちらのバウンス数でも約22 FPSまで低下した。3モデルで2バウンス目を計算・合算するGPU時間は0.51 ms。CPUがGI用に形状を準備する処理には37.93 msかかった。

| シーン内の三角形 | GI RC | 通常再生の平均FPS（3回の中央値と範囲） | 描画間隔 p95 | CPU形状更新 | GPUのGI計算 | GPUの全パス合計 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 90,112 | オフ | 60.0（59.99–60.01） | 17.36 ms | 0 ms | 0 ms | 0.46 ms |
| 90,112 | 1バウンス | 59.1（57.08–59.12） | 19.85 ms | 12.27 ms | 2.48 ms | 4.99 ms |
| 90,112 | 2バウンス | 57.6（55.60–58.43） | 20.96 ms | 12.50 ms | 2.97 ms | 5.46 ms |
| 270,336 | オフ | 60.0（59.51–60.02） | 17.37 ms | 0 ms | 0 ms | 0.49 ms |
| 270,336 | 1バウンス | 21.5（21.27–22.16） | 51.33 ms | 37.61 ms | 2.42 ms | 4.79 ms |
| 270,336 | 2バウンス | 22.7（22.04–22.75） | 46.92 ms | 37.93 ms | 2.95 ms | 5.23 ms |

描画間隔のp95は通常再生で95%のフレームが収まる時間。CPU・GPU各列は別の診断区間のフレーム中央値を、独立した3回の実行で再度中央値にした。CPUとGPUの処理は重なる。両方のシーンで、2バウンス目の追加パスだけを計ると順に0.46 msと0.51 msだった。3モデルでは実行順や回によって通常再生FPSに揺れがあり、バウンスを1回にすると速くなる傾向は見られなかった。

3モデル・2バウンスのCPU形状更新37.93 msの内訳には、ボーン・モーフから頂点位置を取得する処理13.32 ms、三角形の探索構造（BVH）の更新12.43 ms、GPUバッファへの転送要求8.46 msが含まれる。要求サイズは毎フレーム20.25 MiBで、1バウンスでも同量だった。GPU計時がそろった全フレームで、GIオンでは形状更新が1回、GIオフでは0回だった。

解像度だけ1280×720に下げて3モデル・2バウンスを再測定すると、通常再生は22.80、21.94 FPSだった。GPUの描画パスはフルHDの2.15 msから1.88 msに短縮した一方、CPU形状更新は38.05 msだった。このシーンでは解像度を下げても再生速度はほぼ同じだった。

計20回の実機テストが通り、全回でWebGPU検証エラーは0件だった。GPU計時は各回の診断120フレームすべてで取得できた。実行環境の `local-references/rc-gi-stress-playback-2026-11-22/` に集計JSONと、各試行の生データ・固定フレームの画像を含む `measurements.zip` を保存した。

## 比較条件

自作PMXで床・左右の壁・ひだの付いた4つの曲面を描画した。シーン全体は90,112三角形で、床と壁の24,576三角形は静止し、残り65,536三角形は親ボーンの移動、左右のボーンの回転、頂点モーフで変形する。モーフは32,508頂点に作用する。色と形を異ならせた7つの不透明MMD材質を使い、ON時には全90,112三角形がGIに入ったことを照合する。[計測用PMXの生成コード](../test/fixtures/rc-diffuse-gi-stage/stress-scene.mjs)

さらに3モデルを同時に動かす条件を作った。各モデルを0.55倍とし、X座標 −38、0、+38 に並べると、3室が重ならず、最も近いGI領域（一辺128）に収まる。ステージ込みで270,336三角形、うち196,608三角形がボーンとモーフで動く。3室とも画面に入るようにカメラを引いたので、1室と3室の差には画面占有率の違いも含まれる。

Core i9-11900K、GeForce RTX 3070（8 GiB、ドライバー610.60）、メモリ64 GiBのWindows機を使用した。Electron 45.3.1、Babylon.js 9.2.0、WebGPU、GI既定の原点4領域で、通常の影と物理はOFF。1バウンス版は `4740b84`、近距離2バウンス版は `0258af6`。同じ描画サイズ・カメラ・照明・キーフレームで比較した。

各回とも専用のElectronを起動し、エディターの再生ボタンを押す。通常再生は30描画フレームのウォームアップ後に120描画間隔を計測する。平均FPSは平均描画間隔の逆数。次にフレーム0から再生し直し、同じ長さの別区間でCPU処理とGPUパスに計時を入れる。実時間の再生なので、同じ120描画フレームでも進むモーションの長さには差が出る。計時終了後に固定フレームのPNGを比較し、曲面がカメラに映って動いたことも確認する。[連続再生ベンチマーク](../test/e2e/rc-gi-stress-playback.spec.mjs)

## CPU側で次に測る箇所

変形する曲面と同じスケルトンを持つ床・左右の壁は、頂点がすべて静止ボーンに割り当てられている。それでも3室の120フレームで、床・赤壁・青壁それぞれに対して `getPositionData` が360回ずつ呼ばれた。3室を合わせて毎フレーム9回、見た目が動かない面の頂点変形を評価している。現行のキャッシュはスケルトン全体の行列変化を照合し、変形後の座標が前回と一致したら後段で再利用する。[姿勢キャッシュ](../src/render/luminous-radiance-pose-cache.ts)

次の比較候補は、そのメッシュにウェイトを持つボーンだけで姿勢変化を検出できるかどうか。移動・回転・モーフ・逆シークで頂点位置と照明が一致することを条件に、床・壁の再評価、CPU形状更新時間、通常再生FPSへの効果を測る。この計測で分かるのは再評価の回数までで、削減できる時間は未測定。

## 再現

GPUを利用できるWindowsで、リポジトリのルートから実行する。既定は1室・1920×1080で、`MMD_RC_GI_STRESS_MODELS=3` で3室、`MMD_RC_GI_STRESS_WIDTH=1280` で1280×720になる。各回のJSONには描画間隔、CPUとGPUの時間、転送要求量、GPU検証結果を記録する。繰り返し測る際は出力先を回ごとに変更する。

```powershell
$env:MMD_RC_GI_STRESS='1'
$env:MMD_RC_GI_STRESS_OUTPUT="$PWD/local-references/rc-gi-stress-playback-2026-11-22/reproduction-1"
npm.cmd run test:e2e -- rc-gi-stress-playback.spec.mjs --workers=1 --trace off
```

1バウンスの再現には専用の作業コピーを用意し、同じベンチマークと依存関係で、`src/render/` の `mmd-radiance-gi-query-wgsl.ts`、`rc-diffuse-gi-field.ts`、`rc-diffuse-gi-irradiance.ts`、`rc-diffuse-gi-shaders.ts` を `4740b84` の内容にしてGIをONにする。通常の起動設定からバウンス数を切り替える操作はない。
