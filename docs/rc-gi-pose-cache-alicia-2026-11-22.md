# GI RCの頂点変形の再利用とアリシアのダンス再生

## フルHD・2バウンスでの結果

アリシアのダンスと、ボーン・モーフで変形するステージ3室を同時に再生すると、通常再生が19.3 FPSから22.7 FPSに上がった（約17%）。ステージ3室だけでは約25%上がり、アリシアと小さいステージでは修正前後とも約60 FPSだった。

| 再生シーン | GI対象の三角形 | 修正前 FPS（範囲） | 修正後 FPS（範囲） | 描画間隔 p95 前→後 | CPUのGI形状準備 前→後 |
| --- | ---: | ---: | ---: | ---: | ---: |
| アリシアのダンス＋小型ステージ | 24,480 | 60.0（58.53–60.01） | 60.0（60.00–60.02） | 17.58→17.54 ms | 5.76→5.33 ms |
| 高負荷ステージ3室 | 270,336 | 22.2（20.67–22.31） | 27.8（27.72–28.31） | 48.55→39.51 ms | 38.59→28.26 ms |
| アリシアのダンス＋高負荷ステージ3室 | 294,780 | 19.3（18.83–19.36） | 22.7（22.36–22.96） | 56.06→48.19 ms | 42.12→32.87 ms |

FPSは各条件で独立に3回測った通常再生の平均FPSの中央値。描画間隔p95は各回の遅い側の5%に入る境界。CPU時間は別の診断区間のフレーム中央値を、さらに3回の実行で中央値にした。

同時再生では、静止した床・壁の頂点変形が毎フレーム9回から0回になり、頂点位置の取得は15.46→12.32 msになった。GPUへの転送要求は47→7回、CPUが転送を要求する時間は8.15→1.94 ms。送ったデータは前後とも22.94 MiB/フレームだった。GPU上のGI計算は3.59→3.57 msで、改善の大半はCPU側。次に大きく残るのは変形した三角形のBVH更新（14.17 ms）と、頂点位置の取得（12.32 ms）。

2つの変更の寄与を分けるため、姿勢キャッシュだけでも測った。ステージ3室のFPSは修正前22.2、姿勢キャッシュのみ24.2、転送の統合を加えると27.8（各3回）。アリシアと小型ステージでは毎フレーム動く11メッシュすべての頂点変形が必要で、転送は23→3回に減ったものの、FPSは約60のままだった。

計25回の計測でWebGPUの検証エラーは0件、全回で診断120フレーム分のGPU時間を取得した。各シーンの0・60フレームの画像は修正前後で全画素一致し、ダンスの巻き戻しでも元の画像に一致した。同時再生ではアリシアのセンターボーンも0・60フレーム間で0.70移動した。実行環境の `local-references/rc-gi-pose-cache-2026-11-22/` に集計、全試行の生データと比較画像を保存した。

性能計測とは別に、静止姿勢、ボーン・モーフの連続変形、GIの再計算条件、手動・原点領域での2バウンス、旧Skyの逆シーク、アリシアのGI＋Sky再生の計7件を実機で確認した。連続変形の回帰テストはBVHの頂点更新経路をすべて数えるようにし、動く10,000三角形を61回更新した実測と一致した。旧Skyのテストは保存状態を注入した後に効果一覧を開き直して、復元されたカードを操作する。

## 変更

以前の高負荷テストでは、静止した床や壁までもが、同じスケルトンの別のボーンが動くたびにCPUで頂点位置を再計算していた。そこで、各メッシュの頂点に正のウェイトを持つボーンを調べ、その最終変換行列をキャッシュの照合対象にした。親ボーンの動きも最終行列に反映される。頂点・ウェイト・インデックス・モーフの変化は引き続き値で照合する。[前回の高負荷テスト](./rc-diffuse-gi-stress-playback-2026-11-22.md)

Babylon.js 9.2.0の `ApplySkeleton` と照合して、通常の4スロットと追加4スロットを扱い、正のウェイトを持つスロットを選ぶ。隣り合うボーン行列は同じ配列の連続範囲として保持する。インデックスが小数、範囲外、または入力長が不規則な場合は行列配列全体を照合する。実際のスキニングは従来どおりBabylon.jsが行う。[Babylon.jsのボーンとウェイト](https://doc.babylonjs.com/features/featuresDeepDive/mesh/bonesSkeletons/)・[姿勢キャッシュ](../src/render/luminous-radiance-pose-cache.ts)

三角形と探索構造（BVH）をGPUへ送るときは、変更されたメッシュのデータがバッファ上で連続する区間を一度に渡す。既存配列の部分ビューを使うので、連結用のデータコピーは発生しない。途中に更新不要の領域があれば転送を分ける。[転送の実装](../src/render/luminous-radiance-scene.ts)・[転送先の内容を照合するテスト](../src/render/luminous-radiance-scene.test.ts)

## テスト条件

- Windows、Core i9-11900K、GeForce RTX 3070、WebGPU、1920×1080。GI RCは既定の原点4領域と近距離2バウンスを使用し、物理と通常の影はオフ。
- 修正前は `f1bf2f2`。各条件でElectronを起動し直し、GUIから再生。30フレームのウォームアップ後、120描画間隔で通常再生FPSを測る。別の再生区間でCPUのGI形状準備、頂点変形、BVH更新、転送要求、GPU時間を計測した。
- アリシア単独の条件は、指定された `Alicia_solid.pmx` に同梱の `2分ループステップ20.vmd` を読み込み、GI用に36三角形の小さいテストステージを置いた。素材の参照先と扱いは[ローカル素材台帳](./test-reference-asset-ledger.md)に記録している。
- 高負荷条件は、床・壁・ひだのある曲面を合わせた3室（270,336三角形）を動かす。アリシアと同時に動かす条件では、踊りが見えるように3室を奥へ移し、同じカメラで修正前後を比較する。
- 再生計測はフルHD。描画の一致確認は計測後の640×360のPNGを復号し、0・60フレームの全RGBA画素を比較する。アリシアの条件では60から0に戻った画像も確認する。3室との同時再生では、アリシアのセンターボーンの描画位置が0・60フレーム間で動いたことを別途照合する。

## 再現

リポジトリにアリシアと同梱VMDを配置した環境で実行する。アリシアと高負荷ステージを同時に再生する場合は `MMD_RC_GI_STRESS_ALICIA=ensemble` と `MMD_RC_GI_STRESS_MODELS=3` を指定する。結果を比較する際は実行ごとに出力先を分ける。

```powershell
$env:MMD_RC_GI_STRESS='1'
$env:MMD_RC_GI_STRESS_ALICIA='1'
$env:MMD_RC_GI_STRESS_OUTPUT="$PWD/local-references/rc-gi-pose-cache-2026-11-22/reproduction"
npm.cmd run test:e2e -- rc-gi-stress-playback.spec.mjs -g 'GI on' --workers=1 --trace off
```
