# UI 構想メモ（テーマ / 拡大率 / レイアウト）

更新日: 2026-08-05
状態: 構想 / 未実装

## このメモの役割

ダーク／ライトテーマ、UI 拡大率、狭い画面でのレイアウト詰まりについて、方針と順序をまとめる。3つは別々の話に見えるが、**実体は「値を直書きしない」という1本のリファクタの上に乗る。**

前提となるアプリ設定の保存については [入力まわり構想メモ](./input-and-app-settings-concept-2026-08-05.md) を参照。テーマも拡大率も `settings.json` 側であり、**プロジェクトファイルには入れない**（入れると古いプロジェクトを開くたびに配色や倍率が変わる）。

## 大前提: 無彩色

**UI の地色・文字色・境界線は無彩色を使う。ここは譲らない。**

これは好みではなく計測の要件である。視野に有彩色があると目がその色に順応し、画の色を逆方向に判断してしまう。グレーディングの部屋の壁が中性グレーであるのと同じ理由であり、**ダークを既定とする理由（周辺輝度への順応）の色版**にあたる。

ただし制約は「色を使うな」ではなく **「色の面積を作るな」**である。2px の再生ヘッドが彩度を持っていても色順応は起きない。

> **無彩色が地。有彩色は意味を持つものだけ。**

有彩色を許す対象: 再生ヘッド、選択状態、警告・エラー、収録中の赤。地が完全に無彩色であるため、この数点だけが色を持つことで意味が一発で伝わる。

### 実務上の注意

- Tailwind のグレー系パレットはほとんどが色を持つ。`slate` は明確に青寄り、`gray` もわずかに青寄り、`stone` は暖色寄り。**`neutral` が真の無彩色。**現状はカラーコード直指定のため問題ない見込みだが、トークン化の際に確認する
- ダークグレーでは色被りに気づきにくい。**明るくすると一気に見えるようになる**

### エージェント運用

コーディングエージェントは放っておくと青寄りのグレーに寄せてくる（学習データの大半が Web アプリ UI であるため）。毎回口頭で指示するのではなく、AGENTS.md に理由つきで記載する。

> UI の地色・文字色・境界線は無彩色（R=G=B）を使う。青寄り・暖色寄りのグレーを使わない。有彩色は意味を持つ要素に限る。理由: 映像編集ツールとして、UI の色被りが画の色判断を歪めるため。

理由を添えると守り方が安定する。理由のないルールは別の「良さそうな」判断に上書きされやすい。

R=G=B は機械判定が可能なため、将来的に lint ルールや小さいチェックスクリプトに落とせる。トークン化すると色の記述箇所が集約されるため、判定対象も狭くなる。

## テーマ（ダーク / ライト）

### 既定はダークのまま

映像系ツールが暗いのは流行ではなく、周囲が明るいと絵の明るさを誤認するためである。MMD_modoki は PBR とライティングと色を判断する道具なので、**ダークグレー基調は既定として正しい。**ライトは「選べる」のであって「既定を変える」話ではない。

### ライトが必要な理由も本物

好みだけの話ではない。

- 明るい部屋では暗い UI は反射で見づらい
- **乱視の人は暗い背景の明るい文字がにじむ**（ハレーション）。ダークのほうが読みにくい層が実在する
- 事務ソフトに慣れている人

**アクセシビリティ寄りの機能**として扱う。

### 方針: タイムラインも含めて全部明るくする

ビューポートは対象外。それ以外は一貫して明るくする。

タイムラインは実質「表」であり、行と列とセルを持つ。**絵を見る場所ではなくデータを見る場所**なので白地でよい。判断が必要な場所（ビューポート）は暗いまま守られているため、色・明るさ判断の要件は損なわれない。

### 真っ白ではなくライトグレー

好みではなく構造の問題。純白を地にすると**そこから上に行けない**。ダイアログやポップオーバーなど「一段手前に浮かせたいもの」を白より明るくできなくなる。

ライトグレーを地にすると3段の階層が作れる。

```other
沈む（入力欄、タイムラインの地）   ← 少し暗いグレー
地（パネル）                     ← ライトグレー
浮く（ダイアログ、ポップオーバー）  ← ほぼ白
```

これはダークモードと**同じ語彙**である（ダークは暗いグレーが地、明るいグレーが浮く）。トークンは `--surface` / `--surface-raised` / `--surface-sunken` の3つで両テーマに効く。

眩しさの面でも、モニタ輝度での純白は長時間つらく、暗いビューポートとの境界が硬くなる。

### 「ダークを反転すればライト」にはならない

機械的な反転で壊れる箇所がある。

1. **コントラストの作り方が逆。**暗い地では明るくして目立たせるが、白地では暗くする。しかも非対称で、**白の上に暗くする余地は狭い**（すぐ真っ黒に突き当たり全部同じ濃さになる）
2. **入力欄の向きが逆。**ライトでは白（浮いて見える）、ダークではパネルより暗い（沈んで見える）
3. **浮きの表現方法が違う。**ライトは影で浮きを出せるが、ダークでは影がほぼ見えないため明るくして浮かせる
4. **アクセント色はテーマごとに別の値が要る。**暗いグレーの上で映えるピンクは白の上では薄く見える。1色の使い回しは必ずどちらかで負ける

具体的に効いてくる箇所: 再生ヘッド（白地では深いローズ／マゼンタが要る）、キーの菱形（暗い塗り、やや大きめ）、選択行（薄い青系で染める）、グリッド線（白地だとキーと競合してうるさくなりやすい）、波形（濃色の塗りにする）。

### ビューポート関連の分類

|           | 何                 | 保存先               |
| --------- | ----------------- | ----------------- |
| UI テーマ    | パネル、メニュー、文字       | settings.json     |
| ビューポート背景  | 出力に写る＝作品の一部       | プロジェクト            |
| グリッド・ギズモ色 | 出力に写らないが3D空間に描かれる | settings.json（暫定） |

**UI テーマとビューポート背景を連動させてはならない。**連動させると、UI を明るくしただけで書き出した絵が変わる。

### Electron 側

`nativeTheme.themeSource` も併せて設定する。これをしないとタイトルバーだけ暗いまま残り、ライトモードで不自然になる。

選択肢は **ライト / ダーク / システムに従う** の3つ。Tailwind の `dark:` は `media` ではなく **class 戦略**を使う（`media` だと OS 追従しかできず、ユーザーが選べない）。

アイコンが SVG で `currentColor` を使っていれば配色は自動で付く。PNG の場合は2セット必要になるため、要確認。

## UI 拡大率

### フォントサイズ単体ではなく全体の拡大率にする

要望は「フォントサイズを変えたい」として来ているが、フォントだけ大きくするとパネル幅は変わらないため**文字があふれる**。密度の高いエディタ UI では崩壊しやすい。

「表示倍率 100% / 125% / 150%」は OS やブラウザで見慣れた概念であり、ユーザーへの説明も要らない。

### 方式: ルートの font-size を変える（rem）

2つのルートがある。

**A. `webFrame.setZoomFactor()`** — 1行で全体が拡大するが、レンダラ全体にかかるため **WebGPU のキャンバスも巻き込む**。`devicePixelRatio` の報告値が変わるので Babylon の resize が追従するか検証が要る。**最もデバッグが面倒な描画経路を触ることになる。**

**B. ルートの `font-size` を変える** — Tailwind は余白もフォントも既定が rem のため、`html { font-size }` を動かすだけで大半が連動する。

**B を推す。**理由は実装量ではなく、

> **拡大率を CSS だけで完結させれば、描画経路に一切触らない。**

- ビューポートのレンダリング解像度は不変
- **1px のボーダーが 1px のまま保たれる**（全体ズームだと 1.5px 等になりボケる）
- WebGPU 側は拡大率の存在を知らなくてよい

### 2026-08-13 暫定実装の判断

現行 UI はまだ `px` 指定が多く、B をそのまま適用すると一部の文字や余白だけが変化する混在状態になる。そのため v0.2 の実用導線では、先に **A の Electron zoom を限定的に採用**した。

- `ウィンドウ > UI倍率` に 75 / 100 / 125 / 150% を置く
- 倍率はプロジェクトではなくアプリ設定として `localStorage` へ保存する
- 倍率変更後は `resize` を発火し、Babylon viewport と canvas UI の再計測を促す
- PNG連番の別ウィンドウは専用 Electron session と `zoomFactor: 1` で生成し、同一オリジンの倍率共有と出力寸法への混入を防ぐ
- WebM は専用 session では Chromium の VP8 / VP9 encoder が利用不可になるため既定 session を維持する。出力は UI canvas 寸法ではなく明示した RGBA surface 寸法を使う
- `UIを表示` は既存 presentation mode を使い、`Alt+Enter` で切替、非表示中は Tab または Esc で復帰する

B の rem / token 化は引き続き長期方針とする。Electron zoom は現行の px 主体 UI を一様に拡縮するための暫定実装であり、描画品質・pointer picking・低解像度時のレイアウトは実機比較を継続する。

### 難所は canvas 描画部分

rem は CSS の話なので、JS で座標計算して描いている箇所には効かない。`timeline.ts` が canvas 描画であれば、そこは拡大率を読んで行の高さ・文字サイズ・キーの菱形サイズを掛ける実装が要る。

**ライトモードでもタイムラインが最難所であり、2つの機能で同じ場所が難所になる。**逆に言えばタイムラインさえ通れば両方片付く。

### 段階と指定方式

**50 / 75 / 100 / 125 / 150 の5段。**自由なスライダーにすると 137% で崩れる組み合わせまでテストする羽目になる。

上限を 150 にすることで、200% でヘアラインが細くなりすぎる問題も回避できる。段の追加は配列に数字を足すだけで非破壊のため、**狭く始めて必要なら広げる**（可逆な判断）。

**指定はウィンドウ比の相対値ではなく絶対値。**理由:

1. ウィンドウを広げる目的は「もっと多く見たい」であり、連動させると情報量が増えない
2. リサイズ中に文字サイズが動くとアプリが不安定に見える
3. 文字を大きくしたい人が最大化すると**文字が小さくなる**（要望と真逆）

VS Code、Blender、Photoshop、ブラウザいずれも絶対指定。

サイズは絶対、配分は相対、という切り分けになる。

|          | 方式                  |
| -------- | ------------------- |
| UI 拡大率   | 絶対値（ユーザーが選ぶ）        |
| パネルの割り付け | 相対（flex / % / grid） |
| ビューポート   | 残りを埋める              |

### 低倍率（50 / 75）には2つの用途がある

1. **OS の拡大率を打ち消す。**Windows の 4K ノートは既定で 150〜200%。アプリ 100% が実効 150% になる
2. **小さい画面に詰め込む。**1366x768 で 75% にすれば、広い画面前提のレイアウトが収まる

**設定画面に実効倍率を表示する**とよい（「アプリ 75% × OS 150% = 実効 112%」）。これが無いと「50% にしても小さくならない」で混乱する。

### その他

- **最小ウィンドウサイズも拡大率で掛ける。**150% にしたら UI が入らない、が起きる
- **保証範囲を分ける。**100 / 125 / 150 は崩れないことを保証、50 / 75 は best-effort。手動チェックリストの通り数を抑える
- 初回起動時にのみ DPI を見て既定値を推測する案はあり得るが、その後はユーザーの絶対指定とする

## トークン整理（上2つの前提）

Tailwind を入れたのは v0.2.0 のときで、まだ荒く、絶対値と相対値が混在している。

### 単独のリファクタにしない

「CSS を整理する」を単独タスクにすると終わりがなく、成果が見えず、エージェントに投げると余計な「改善」が入る。

**ライトモードと UI 拡大率の準備として行う。**そうすると完了条件が外から決まる。

- ライトモードが成立する ＝ 色のトークン化が足りている
- 125% で崩れない ＝ 寸法の相対化が足りている

**外部にテストがあるリファクタは有界、無いリファクタは無限。**

### 最強の縛り: 見た目が変わったらバグ

色をトークンに置き換える作業も px を rem にする作業も、**やった後の見た目は完全に同じであるべき**である。値の表現方法を変えるだけで、値そのものは変えない。

これを完了条件にすればレビューが一瞬で済む（「気づかないなら成功」）。エージェントが余計な変更をしたら即座に分かる。**デザインを直したくなってもその回ではやらない。**

### 2回に分ける

1. **色のトークン化** → 完了条件はライトモードが1テーマ足せること
2. **寸法の相対化** → 完了条件は 125% で崩れないこと

同時にやると、崩れたときに原因が2つになる。

### 色トークンの案

10個程度に抑える。多いと守られなくなる。

```other
--surface / --surface-raised / --surface-sunken
--border
--text / --text-muted
--accent   （現状のピンク系）
--danger
--selected
```

### 寸法のルール案

- **rem**: 文字サイズ、余白、パネル幅
- **px**: 境界線（1px を保つ）、アイコンサイズ
- **flex / grid / %**: レイアウトの比率
- 固定 px の幅・高さは原則使わない

### 最初の一手: 棚卸し

Tailwind の既定スケールは元々 rem なので、混在の出どころはほぼ2つに絞られる。

- **任意値** — `w-[320px]`、`text-[13px]`、`p-[7px]`
- **JS のインラインスタイル** — `style.width = ...`

```other
grep -ro '\[[0-9.]*px\]' src/ | sort | uniq -c | sort -rn
```

これで仕事量が見える（50箇所なら半日、400箇所なら分割）。**変更ゼロ、クォータゼロ。**一覧を見れば「残していい px（ボーダー、アイコン）」と「直すべき px（幅、高さ、余白、文字）」の区別も付く。

### タイムラインを最初にやる

簡単なところから始めたくなるが逆を勧める。パネルやメニューは容易であり、先にやると「トークン10個で足りる」と思い込んだまま最後にタイムラインで足りないことに気づく。

**タイムラインが白地で成立すれば、トークン設計が十分だと証明できる。**残りは埋めるだけ。

### 副産物

白地にするとレイアウトの粗（1px のズレ、余白の不揃い、微妙な高さ違い）が全部見える。ダークグレーでは見えないものが白では目に刺さる。**ライトモードを作る作業は無料のレイアウト点検を兼ねる。**

## レイアウトの詰まり

### 発端

開発環境は 4K ディスプレイで、MMD_modoki を 2K ほどのサイズで開いて作業している。**レイアウトが広い画面前提になっている可能性が高い。**

下パネルには 情報 / 補間 / ボーン / 照明 / 影 / アクセサリー が横に6つ並んでおり、これは 2K 幅だから成立している。1920x1080 では相当きつく、1366x768 では破綻する可能性がある。

### 「フォントが小さい」の正体かもしれない

狭い画面の人が見たものを言葉にすると「文字が小さい」になる。実際に起きているのは「詰め込みすぎて各要素が縮んでいる」である。

**だとするとフォントサイズ設定を足しても解決しない**（大きくすればもっと入らなくなる）。要望への対応の前に、実際の壊れ方を見る必要がある。

### 縦と横で足りないものが違う

1920x1080 も 1366x768 も 16:9 であり、**縦が薄い。**

- **横を食っている** → 右のエフェクト欄、下パネルの6セクション横並び
- **縦を食っている** → 上のタイムライン、下パネルの高さ

したがって**下パネルを折り返して2段にするのは悪手**である。横は解決するが、一番足りない縦を追加で food う。レスポンシブの定番手が使えない。

### 分類の基準: 常時か随時か

常に見えている必要があるもの: ビューポート、タイムライン、いま触っているものの数値（情報・補間・ボーン）。

触るときだけ見えればよいもの: 照明、影、アクセサリ、エフェクト。設定して、しばらく放置するもの。

**基準を1本決めると配置が自動的に決まる。**

### 対策（安い順）

1. **パネルの表示トグル。**メニューに「エフェクト欄を表示」「下パネルを表示」のチェックとショートカット。実装は表示／非表示だけ。狭い人は畳めて、広い人には何の影響もない。**リスクほぼゼロで最も効く**
2. **下パネルを「常時」と「随時」に割る。**情報・補間・ボーンは出しっぱなし、照明・影はタブか折りたたみ。アクセサリ欄が対象セレクタ側へ抜ければ残りは2〜3個なので、タブにしても煩雑にならない
3. **低倍率（75%）。**トークン整理のついでに手に入る
4. **パネルのリサイズ（分割バー）。**理想ではあるが、状態保存・最小幅・ドラッグ処理・拡大率との相互作用があり重い。後回し

### 最小サポートサイズを宣言する

これが無いと「窮屈」が無限に続く。決めれば手動チェックリストに具体的な数字が載り、「そこで破綻しないこと」が完了条件になり、それ以下は非対応と言い切れる。

**1280x720 を最小とする案。**1366x768 も 1920x1080 も自動的にクリアする。

### 今日できる一手

**自分のウィンドウを 1280x720 と 1920x1080 にして眺める。**コードを触らず、クォータも使わない。壊れ方を見ないとどの対策が効くか決められない。

手動チェックリストに常設項目として追加する（一度直しても、次の機能追加でまた詰め込むため）。

## やらないこと

- **UI テーマとビューポート背景の連動**
- **キーバインド・テーマ・拡大率のプロジェクトファイルへの保存**
- **ダークの色を機械的に反転してライトを生成すること**
- **CSS 整理を単独タスクとして立てること**
- **色と寸法の整理を同時にやること**
- **下パネルの2段折り返し**（縦を食う）
- **パネルの分割バー**（当面）

## 未決定事項

- 要望を出した人が 150% で足りるかどうか（OS 拡大率の設定値を確認できるとよい）
- 最小サポートサイズの確定
- グリッド・ギズモ色を設定側に置くかビューポート側に置くか
- アイコンが SVG（`currentColor`）か PNG か
- `webFrame.setZoomFactor()` を実験として試すかどうか
- 初回起動時の DPI 推測を入れるか

## 補足

UI は今日整理した中で**唯一、器械で守れない領域**である。外部親は final matrix で assert でき、VMD はラウンドトリップで検証でき、書き出し速度は ms で測れるが、UI の感触には `assert` が書けない。

計測器は「自分で触る」と「他人に触ってもらう」の2つだけである。狭いウィンドウで眺めることも、要望をくれる人も、その計測器にあたる。
