# v0.2.x リリースフィードバック台帳

更新日: 2026-08-28

v0.2.0 以降に届いた不具合、要望、UX 上の課題、仕様確認を、v0.2.3 のリリース準備を含めてまとめて管理する。
初回棚卸しでは、GitHub Issues のうち v0.2.0 リリース日の 2026-07-06 以降に作成されたもの、その期間に完了確認された継続 Issue、X の公開キーワード検索で確認できた投稿を対象にした。

リリースノートに記載済みの既知の制限は、実際の追加報告や想定外の挙動がない限り、この台帳の件数には含めない。

## 運用ルール

- ID は `V022-001` の形式で付ける。
- `対象` には、報告者が確認したリリースを記録する。複数リリースにまたがる場合は範囲で示す。
- 種別は `bug` `request` `spec` `ux` `docs` `investigation` を使う。
- 優先度は `P0` `P1` `P2` `P3` を使う。
  - `P0`: データ消失、起動不能、主要機能が広範囲で使用不能になる。
  - `P1`: MMD の主要編集・保存・出力経路に大きく影響する。
  - `P2`: 回避策がある、条件依存、または実験機能に限定される。
  - `P3`: 軽微な表示、文言、使い勝手、将来改善の候補。
- 状態は `collecting` `investigating` `needs retest` `fix planned` `fixed` `won't fix` `duplicate` を使う。
  - `needs retest` は、関連修正が入った可能性はあるが、元の再現条件で改善を確認できていない状態とする。
- 1 件追加したら「一覧」と「詳細」の両方を更新する。
- GitHub Issue 1 件に複数の症状や要望が含まれる場合は、症状単位で台帳 ID を分ける。
- 過去リリースからの継続案件は、元 Issue または元台帳 ID を詳細に残す。
- 修正作業へ進める項目は、必要に応じて `mmd-basic-task-checklist.md` にタスクを追加し、この台帳から参照する。
- 原因が複数領域にまたがる場合や調査記録が長くなる場合は、個別の調査メモを作り、この台帳は要点とリンクに留める。

## 詳細

### V022-001 Apple Silicon 上で macOS x64 配布物の動作が非常に遅い

- 種類: bug
- 優先度: P1
- 対象: v0.1.x〜v0.2.0
- 発生日: 2026-03-24
- 送信元: [GitHub Issue #5](https://github.com/togechiyo/MMD_modoki/issues/5)
- 状態: fixed
- 環境: M1 Pro / macOS 15.7.4
- 現象: x64 配布物ではモデル読込に1分以上かかり、操作時に10〜20 FPSまで低下する。ARMネイティブのローカルビルドは軽快に動作した。
- 結果: v0.2.0 で Apple Silicon 向け配布物を追加し、Issue は 2026-07-09 に完了としてクローズされた。
- メモ: v0.2.2 では macOS arm64 DMG を継続して配布している。

### V022-002 `mmd-manager.ts` の文字化けコメントでファイルが異常に肥大化

- 種類: bug
- 優先度: P2
- 対象: v0.1.x〜v0.2.0
- 発生日: 2026-03-24
- 送信元: [GitHub Issue #5 のコメント](https://github.com/togechiyo/MMD_modoki/issues/5)
- 状態: fixed

- メモ: 今後も意味を復元できない文字化けコメントは、挙動へ影響しないことを確認して除去する。

### V022-003 Linux / macOS で PMX テクスチャが白くなる

- 種類: bug
- 優先度: P1
- 対象: v0.2.0
- 発生日: 2026-07-06
- 送信元: [GitHub Issue #13](https://github.com/togechiyo/MMD_modoki/issues/13)
- 状態: fixed
- 環境: CachyOS / AMD RX 6400、および macOS 15.7.7 arm64。Windows 11 では表示できた。
- 現象: v0.1.8 では表示できた PMX のテクスチャが v0.2.0 で白くなった。
- 原因 / 対応: POSIX の file URL とテクスチャパス解決を修正した。関連コミットは `789e6af`。
- 結果: Linux と macOS の両報告者が v0.2.1 で改善を確認し、Issue は完了としてクローズされた。
- X 追加報告: 2026-07-07、`@kakurakutekiko1` から、アペミク以外の複数モデルと過去 project が白くなる報告があった。2026-07-07〜08、`@KMmder` からも一部テクスチャが表示されない報告があり、v0.2.0 の同系統事例として統合した。
- v0.2.1 追跡: `@kakurakutekiko1` がモデル全体の白化改善を確認した一方、瞳欠けと半透明材質の問題は残ったため、V022-024 / V022-025 へ分離した。
- 関連: [macOS / Linux file URL テクスチャ白化調査](./mac-linux-file-url-texture-whiteout-2026-07-14.md)

### V022-004 macOS でモデル配置先によりテクスチャ読込結果が変わる

- 種類: bug
- 優先度: P1
- 対象: v0.2.1〜v0.2.2
- 発生日: 2026-07-18
- 送信元: [GitHub Issue #18](https://github.com/togechiyo/MMD_modoki/issues/18) 1-1 / [GitHub Issue #21](https://github.com/togechiyo/MMD_modoki/issues/21)
- 状態: needs retest
- 環境: M4 Mac mini / macOS 15.7.7〜15.7.9
- 現象: 外部ドライブ上のモデルは正常だが、起動ドライブのユーザーフォルダ上に置いた同系統モデルはテクスチャが白くなる。
- メモ: v0.2.0 の POSIX file URL 修正後の報告であるため、V022-003 と同一原因とは断定しない。Unicode 正規化、空白、記号、ファイルアクセス権、相対テクスチャパスを切り分ける。
- 2026-08-25 追加報告: v0.2.2 / macOS 15.7.9 でも、内蔵ドライブのユーザー領域では白化し、外部ドライブへコピーすると表示できる。報告者による「macOS がパスを書き換えるため」という説明は仮説であり、原因確定前に分離して検証する。
- 2026-08-25 修正履歴確認: POSIX の root URL と file URL から local path への変換は `789e6af` で修正され、v0.2.1 と v0.2.2 の両方へ収録済み。macOS 実機で同修正後の白化改善も確認されている。
- 残確認: Issue #21 の報告は修正収録後のため、元の一般的な POSIX URL 白化とは別条件か、同じ model / 配置で修正が効いていないのかをログ付きで再確認する。新しい修正へ直ちに進めず `needs retest` とする。

### V022-053 動画出力の物理が硬く見え、演算レートを調整したい

- 種類: investigation
- 優先度: P2
- 対象: v0.2.2
- 発生日: 2026-08-25
- 送信元: [GitHub Issue #21](https://github.com/togechiyo/MMD_modoki/issues/21)
- 状態: investigating
- 環境: M4 Mac mini / 16 GB / macOS 15.7.9
- 現象: MMD_modoki の動画出力では髪や skirt の動きが viewport より硬く見えるとの所感があり、physics dialog の60 Hzを30 Hzへ変更する手段が求められた。
- 未確定点: 報告内の「FPS 上昇で物理演算回数が倍になり重力の影響が増す」という説明は nanoem での経験に基づく仮説であり、MMD_modoki の原因としては未確認。
- 確認観点: viewport / export の fixed timestep、出力 FPS、substep 数、gravity、warm-up、同一初期状態での軌跡を比較する。standard physics と experimental runtime を混在させない。
- メモ: 物理 rate の公開設定は結果の再現性と project 保存互換へ影響するため、調査前に要望どおり実装しない。
- 2026-08-25 現行仕様確認: standard physicsはMMD本体寄せで60Hz、fixed timestep `1/60`に固定される。WebMは出力FPSに応じてrender deltaを `1/fps` 秒進めるため、30fpsは概ね2 substep/frame、60fpsは1 substep/frameとなり、実時間1秒あたりの物理stepはどちらも60回になる。「60fps出力で重力計算が倍になる」という仮説は現行実装には当てはまらない。硬さの見た目は同じ初期snapshotとassetで別途比較する。

### V022-054 macOSで`.x`読込後のPNG出力が初期化待ちのまま完了しない

- 種類: bug
- 優先度: P2
- 対象: v0.2.2後のmain
- 発生日: 2026-08-28
- 送信元: プロジェクト所有者によるローカル実機確認
- 状態: fixed
- 環境: MacBook Pro 17,1 / Apple M1 / 16 GB / macOS 26.3.1 / arm64 / WebGPU。Windows環境では同じ現象は未発生との報告。
- 現象: PMXと`.x`を読み込んだ状態で1920x1080 PNGを保存すると、待機が長時間続き出力が完了しない。
- 実機log: `.x`なしの同解像度PNGは約1.68秒で完了した。対象`.x`本体は約1.8秒で読み込まれ、1 Mesh、逆向き重複面2935と記録された。1回目のPNG出力は開始から約266秒後にexport surface準備へ到達したが完了logがなく、2回目は9分30秒以上surface準備へ到達しなかった。停止中のmain / GPU / renderer processはsleep状態でCPU使用率0%だった。
- fixture確認: 初期確認ではユーザー所有asset本体を参照せず、512個の小さい豆腐を1 Meshへまとめ、逆向き重複面を2935個含む配布可能な`tofu-grid-reversed-duplicates.x`を作成した。M1 macOS / WebGPUでPMX豆腐と同時に読み込み、detached exporterから1920x1080 PNG 1枚を約1.97秒で完了した。exporter内部計測は約686ms、`redundantFaceCount`は2935だった。
- 許可assetでの再現: 所有者から利用許可を得た対象`.x`を配布fixtureのPMX豆腐と組み合わせた。asset読込は約1.46秒で完了したが、WebGPU通常条件ではexporterが`initialize app`から先へ進まず、PNG未生成のまま8分でPlaywright timeoutした。timeout時はowner rendererとGPU processが継続してCPUを使用し、exporter rendererは低負荷だった。
- backend / owner描画A/B: 同じsceneをWebGL2へ切り替えると約4.97秒でPNG出力が完了した。WebGPUのままowner viewportのauto-renderをexport開始前に停止すると約3.89秒で完了した。owner windowを隠すだけでは、exporterの`backgroundThrottling: false`によりprocess全体へtimer throttling無効が適用され、owner描画が継続したため回避にならなかった。
- 原因判断: 逆向き重複面数だけでは停止を再現しない。macOS WebGPUで、負荷の高いXをowner viewportが描画し続ける状態とhidden exporterの2つ目のWebGPU engine初期化が競合する条件を確認した。PNG encode / saveへ到達する前に停止するためencoder単体は原因ではない。
- 修正: background exportのactive state bridgeで、PNG / WebM出力の開始時にowner viewportのauto-render状態を保存して停止し、全出力の完了・失敗・cancel後に元の状態へ復帰するようにした。複数出力が重なった場合も最後のactive stateが解除されるまで停止を維持する。
- 修正後の実機確認: M1 macOS / WebGPUで、配布fixtureは1920x1080 PNG 1枚を約1.66秒で完了した。利用許可済みのローカルassetを使った元の再現条件でもasset読込は約1.46秒、PNG出力は約3.31秒で完了し、出力中のauto-render停止と完了後の復帰を確認した。WebMのcancel / retryでも停止と復帰を確認した。
- 自動確認: `MMD_MODOKI_RUN_PNG_STRESS=1 npm run test:e2e -- test/e2e/png-export-stress.spec.mjs -g "X grid"`、`npm run test:e2e -- test/e2e/webm-progress-cancel.spec.mjs`。ローカルasset確認は環境変数で明示した許可済みassetがある場合だけ実行し、未配置環境ではskipする。
