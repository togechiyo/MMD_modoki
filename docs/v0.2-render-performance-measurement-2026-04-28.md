# v0.2 描画負荷計測メモ 2026-04-28

## 目的

v0.2 の物理演算分割と `MmdWasmRuntime` 切り替え PoC 後に、再生 FPS の主因が物理演算か描画側かを切り分けるため、`mmd-manager.ts` に一時的な frame performance log を追加して実測した。

このメモは、2026-04-28 時点のユーザー確認結果と暫定判断を残す。最適化方針の確定ではなく、次に見るべき箇所を絞るための記録として扱う。

## 計測方法

- renderer の render loop 周辺を 10 秒ごとに集計
- `frameTotal` / `sceneRender` / `manualPlayback` / `motionBlur` / `backgroundVideo` / `frameStateUpdate` を計測
- `onBeforeRenderObservable` 内の editor 系更新を区間計測
  - `cameraMotionToViewport`
  - `viewportCameraInput`
  - `boneGizmo`
  - `boneVisualizer`
  - `rigidBodyVisualizer`
  - `editorDof`
- Babylon `SceneInstrumentation` から次を取得
  - active meshes / total vertices
  - active meshes evaluation time
  - animations time
  - physics time
  - render targets render time
  - render time
  - camera render time
  - particles / sprites render time
  - frame time
  - draw calls

注意点:

- Babylon `physicsTime` は Bullet MPR 経路では 0 になりやすい。物理 step は別途 `physics performance sample` の `physicsStepAvgMs` を見る。
- 計測コード自体にもわずかな負荷があるため、絶対値より比較傾向を重視する。
- DevTools 表示中の計測なので、最終的な配布時性能とは一致しない可能性がある。

### 有効化方法

frame performance log は通常時の負荷とログノイズを避けるため、デフォルト OFF とする。

DevTools console から次を実行して再起動すると有効化できる。

```js
localStorage.setItem("mmd_modoki.framePerfLog", "true");
```

無効化する場合:

```js
localStorage.setItem("mmd_modoki.framePerfLog", "false");
```

有効時のみ Babylon `SceneInstrumentation` を作成し、`frame performance sample` を 10 秒ごとに出力する。

## 計測結果

### 中量級モデル 4 体、影あり

条件:

- 中量級モデル 4 体
- ステージあり
- Classic runtime
- Bullet MPR
- 影あり

主な値:

| 項目 | 値 |
| --- | ---: |
| `frameTotal.avgMs` | 28.289 ms |
| `sceneRender.avgMs` | 28.030 ms |
| `activeMeshes` | 215 |
| `totalVertices` | 529,941 |
| `activeMeshesEvaluationTime.average` | 0.786 ms |
| `animationsTime.average` | 2.182 ms |
| `physicsTime.average` | 0 ms |
| `renderTime.average` | 8.866 ms |
| `cameraRenderTime.average` | 12.795 ms |
| `drawCalls.current` | 1,067 |

観察:

- `frameTotal` のほぼ全体を `sceneRender` が占めている。
- `manualPlayback`、timeline、bone visualizer、rigid body visualizer などの editor 更新は、この条件では主因ではない。
- draw calls が 1,000 を超えており、影ありの camera render 系コストが重い。

### 中量級モデル 4 体、影なし

条件:

- 上記と同系統の 4 体プロジェクト
- 影を切った状態

主な値:

| 項目 | 値 |
| --- | ---: |
| `frameTotal.avgMs` | 16.326 ms |
| `sceneRender.avgMs` | 16.081 ms |
| `renderTime.average` | 5.251 ms |
| `cameraRenderTime.average` | 8.183 ms |
| `activeMeshes` | 215 |
| `totalVertices` | 529,941 |

観察:

- 影ありと比べて `frameTotal.avgMs` が約 12 ms 改善した。
- FPS 表示も 30 FPS 台から 50 FPS 台まで改善している。
- 同じモデル数・頂点数で大きく変わるため、この条件では物理演算より影生成 / 描画パスの影響が大きい。

### モデル 1 体 + ステージ 1、エフェクト多め

条件:

- モデル 1 体
- ステージ 1
- エフェクト多め
- FPS 表示は約 47 FPS

主な値:

| 項目 | 値 |
| --- | ---: |
| `physicsStepAvgMs` | 2.158 ms |
| `physicsStepMaxMs` | 7.29 ms |
| `frameTotal.avgMs` | 14.306 ms |
| `sceneRender.avgMs` | 13.607 ms |
| `editorDof.avgMs` | 6.419 ms |
| `frameStateUpdate.avgMs` | 0.691 ms |
| `activeMeshes` | 63 |
| `totalVertices` | 431,661 |
| `activeMeshesEvaluationTime.average` | 0.192 ms |
| `animationsTime.average` | 0.503 ms |
| `renderTime.average` | 4.060 ms |
| `cameraRenderTime.average` | 5.323 ms |
| `frameTime.average` | 10.770 ms |

観察:

- モデル数が少ないため、4 体ケースとは負荷の形が違う。
- `physicsStepAvgMs` は約 2.2 ms で、無視はできないが FPS 低下の主因とは言い切れない。
- `editorDof.avgMs` が約 6.4 ms と大きく、エフェクト盛り条件では DoF 更新経路が疑点になる。
- `sceneRender` は依然として支配的だが、内訳としては影だけでなく DoF / post effect 側も見る必要がある。

## 暫定判断

### 物理演算は今回の主因ではなさそう

`MmdWasmRuntime` 切り替え PoC、Classic / WASM 比較、物理 OFF 比較の結果から、少なくとも中量級モデル 4 体プロジェクトでは物理演算だけが FPS を決めているわけではない。

物理 OFF でも 40 FPS 前後に留まったため、物理演算最適化だけで 60 FPS に届く状況ではない。

### 影が大きい

4 体プロジェクトでは、影ありから影なしにしたときの改善幅が大きい。

現行の影設定は品質寄りで、特に複数モデル + ステージの条件では `sceneRender` / `cameraRenderTime` / draw calls 側に強く効いている可能性が高い。

今後見る候補:

- 影品質プリセット
- shadow map サイズ
- 影描画距離 `shadowMaxZ` の既定値見直し
- contact hardening / transparency shadow の切り替え
- 影対象 mesh の絞り込み
- CascadedShadowGenerator の再検討

### DoF 更新経路も見る価値がある

エフェクト多めの単体モデル条件では `editorDof` が大きく出た。

これは最終的な post effect 描画コストそのものではなく、editor 側で毎 frame 実行している DoF focus / FStop 更新処理の可能性がある。`updateEditorDofFocusAndFStop()` の中で、対象探索、距離計算、pipeline パラメータ反映、UI 同期が毎 frame 走っているなら、dirty check や target cache で下げられる可能性がある。

## 次に見る候補

優先度順:

1. 影あり / 影なし / 影品質プリセット別の比較を同一 4 体プロジェクトで取る
2. `editorDof` の内訳計測を追加する
3. `updateEditorDofFocusAndFStop()` の dirty check / cache 化を検討する
4. draw calls が多いシーンで、影対象と material / submesh 数の関係を見る
5. `MmdWasmRuntime` は性能改善の本命ではなく、互換性確認済みの実験 runtime として扱う

## v0.2 での扱い

v0.2 の物理分割は続ける価値があるが、FPS 改善の次の本命は物理ではなく描画・影・post effect 側に移ったと見る。

ただし、最重量モデルは MMD 本家でも 1 FPS を割るクラスであり、v0.2 の性能保証対象からは外す。中量級モデル 4 体プロジェクトを現実的なベンチマークとして使う。

現時点の方針:

- 物理 backend は Classic / WASM を切り替え可能な状態で維持
- FPS 改善は shadow / DoF / post effect / draw calls の調査に移す
- 影描画距離は、既存プロジェクトの保存値を尊重しつつ、新規既定値を `4800` から `1000` に狭める
- 情報欄にモデル単位の `影` チェックを追加し、主役以外のモデルを shadow caster から外せる逃げ道を用意する
- 計測ログは当面 dev 用として残し、最適化後に削除または debug flag 化する

## 参考実測: 同一モデル 3 体 + FrameGraph（2026-08-14）

ユーザー環境で、同一の `Tda式初音ミクV4X_Ver1.00` を 3 体読み込み、モーション再生中の FPS 表示を比較した。

共通条件:

- WebGPU / WGSL
- Bullet HPR Buffered
- 同一モデル 3 体
- モーション再生中
- モデルの影を使用

| FrameGraph 状態 | 表示 FPS | 1 frame の参考換算 |
| --- | ---: | ---: |
| モーションブラー / ルミナス / SSGI をすべて OFF | 45 FPS | 約 22.2 ms |
| モーションブラー / ルミナス / SSGI をすべて ON | 14 FPS | 約 71.4 ms |

3 効果をまとめて有効にした条件では、表示 FPS は 45 から 14 へ低下し、参考換算の frame time は約 3.2 倍になった。複数モデル条件でも post effect 側の負荷が大きいという従来の暫定判断と整合する。

ただし、スクリーンショットは OFF が frame 1582、ON が frame 1764 で、同一フレームの A/B 比較ではない。GPU、解像度、各エフェクト設定値、FPS 表示の平均化区間も未記録である。この値は性能保証や個別効果の寄与率ではなく、実利用条件での参考値として扱う。次回の厳密比較では同一フレームを停止表示し、モーションブラー、ルミナス、SSGI を 1 つずつ切り替えて計測する。
