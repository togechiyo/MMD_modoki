# v0.2 作業メモ

更新日: 2026-04-28

## 目的

v0.2 系では、v0.1 系のバグ修正ラインとは分けて、Babylon.js と babylon-mmd の新しい機能・改善を取り込む。

単なる依存更新ではなく、MMD_modoki 側で実際に価値が出る機能を有効化・検証することを目的にする。特に babylon-mmd の物理演算まわりを重めモデルでも扱いやすくする。

v0.1.9 は基本的に安定版向けのバグ修正として扱い、v0.2 系の依存更新や挙動変更を不用意に混ぜない。

このメモは、v0.2 で必ず全部実装する約束ではなく、忘れないための候補リストでもある。実装より調査・保留判断・知見の記録で止める項目があってよい。

## 2026-04-28 時点の現在地

完了済み:

- babylon-mmd 1.2.0 / Babylon.js 9.2.0 前提で、Classic と WASM/MPR を切り替え可能にした
- package 版で MPR worker helper / wasm asset を統合した
- `mmd-manager.ts` から物理 runtime 制御を分割し、Classic / WASM の両方で動作確認した
- 物理 backend 表示と physics step 計測を入れた
- 中量級モデル 4 体、最重量モデル、物理 ON/OFF で比較した
- 物理よりも shadow render / scene render 側の影響が大きいケースを確認した
- frame performance log と scene render 内訳計測を feature flag 化した
- 影描画範囲の既定値を `4800` から `1000` に縮小した
- モデル単位の遮蔽影 caster ON/OFF を情報欄から切り替え可能にした

現時点の判断:

- WASM/MPR 化は安定性と切り替え可能性の面では有効だが、FPS 改善は限定的
- 通常確認・手動テスト・回帰確認は互換性優先で Classic を基準にする
- WASM/MPR は重めモデル比較や物理まわり変更時の追加確認用として残す
- 4 体程度の中量級プロジェクトでは、物理より shadow render / camera render / DoF など描画側を優先して見る
- DoF は Frame Graph 化で触る可能性が高いため、今の段階で単独最適化を深追いしない
- 最重量モデルは MMD 本体でも極端に重いケースとして、v0.2 の主要最適化対象からは外してよい

次に優先する候補:

1. Frame Graph PoC
2. DoF / Bloom / LUT / SSAO の順序整理
3. WebGPU / WebGL2 fallback の描画回帰確認
4. MMD 相当タイムライン項目の設計再開
5. 出力確認

## 基本方針

- MMD 本体機能を優先する
- 汎用 3D アプリ化や実験機能の拡張は、依存更新の安定確認より後に回す
- 大きい依存更新は 1 グループずつ進める
- 依存を上げるだけで終わらせず、取り込む機能と検証結果を明示する
- タスクは「実装するもの」だけでなく、「調査して見送るもの」も含めて管理する
- 破綻が出たら、無理に直し切るより原因範囲と再現条件をメモに残す
- v0.1 系へ戻す可能性がある修正は、v0.2 ブランチ内でも切り分けて考える

### Frame Graph 標準化方針

v0.2 では、描画・ポストエフェクト・出力前処理の標準経路を Frame Graph ベースへ寄せられるか検証する。

ただし最初の PoC では、MMD モデル本体のメイン描画は既存経路を維持し、DoF / Bloom / LUT / SSAO / 空気遠近などの後段エフェクトだけを Frame Graph 系へ寄せる。

狙い:

- SSAO / DoF / Bloom / LUT / 空気遠近 / Fog / LuminousGlow / WebM capture の順序を明示的に管理する
- Babylon 8 時代に RenderingPipeline 内で固定されがちだった DoF などを、差し替え可能な描画タスクとして扱えるか検証する
- WebGPU と WebGL2 fallback の違いを、描画経路ごと比較できるようにする
- 既存の独自 PostFX / workaround を、公式タスクで置き換えられるものと残すものに分ける
- 中間 render target の責務を整理し、WebM 出力や高品質出力専用の経路を作りやすくする

最初の PoC:

- [ ] MMD scene color を Frame Graph 経由で最終出力する
- [ ] depth texture を使う DoF を Frame Graph 上で動かす
- [ ] DoF / Bloom / SSAO の順序を 2 パターン以上で比較する
- [ ] LUT は後段タスクとして残し、v0.2 初期 PoC では Classic backend の安定経路を優先する
- [ ] LUT を Frame Graph 化する場合は、既存 `.3dl` / `.cube` と intensity UI を活かせる独自 task 方式を検討する
- [ ] MMD outline が DoF 前後どちらに乗るべきか比較する
- [ ] PMX の透過材質、髪、スカート、アクセサリが depth / DoF で破綻しないか確認する
- [ ] WebGPU と WebGL2 fallback で同じ構成が起動できるか確認する
- [ ] WebM capture 用に、画面表示とは別の後段構成を持てるか確認する

移行条件:

- MMD Standard material / toon / sphere / texture / 透過が既存経路と大きく乖離しない
- babylon-mmd の `MmdOutlineRenderer` と競合しない
- WebGPU で起動し、WebGL2 fallback でも最低限の表示が壊れない
- 既存プロジェクト保存値の互換性を壊さない
- Frame Graph が使えない場合に、最低限の描画へ戻せる

注意:

- Frame Graph はエフェクト品質そのものを自動で上げる機能ではなく、描画タスクとリソース依存を整理する基盤として扱う
- DoF は depth texture 依存のため、透過材質や outline との順序で見た目が変わりやすい
- 空気遠近は既存 Fog とは別に、遠景を環境色へなじませる軽い color grading pass として検討する
- v0.2 では既存パイプラインの即削除ではなく、Frame Graph 経路を標準候補として作り、安定確認後に旧経路を整理する

- MMD カメラ

MMD_modoki 側で自前実装する対象:

- 照明
- セルフ影 / 影設定
- 重力
- アクセサリ
- scene object
- 将来の OBJ / 点群など、MMD モデルではないオブジェクト

このため、v0.2 で増やす非 PMX / 非カメラ項目は `modoki-owned tracks` として扱う。

`modoki-owned tracks` で必要になるもの:

- キーフレーム格納形式
- 補間またはステップ評価の仕様
- 現在フレームの値評価
- scene / UI への値反映
- プロジェクト保存 / 読み込み
- undo/redo との接続
- タイムライン表示上のカテゴリ・色・選択挙動

実装時は、babylon-mmd の runtime に無理に押し込まず、`MMD_modoki` 側で frame evaluation service のような層を持つ案を第一候補にする。

## リスク

- Babylon 9 系では、材質・ポストエフェクト・WebGPU 周辺の細かい挙動差が後から見つかる可能性がある
- `babylon-mmd` 更新により、物理・モーフ・MMD ランタイム内部の挙動差が出る可能性がある
- Electron / Vite / Forge を同時に上げると、ビルド不具合と描画不具合の切り分けが難しくなる
- `@electron/fuses` 2 系は、現行の `@electron-forge/plugin-fuses@7.11.1` の peer dependency と合わない可能性がある
- Babylon 公式機能へ置き換える場合、起動確認だけでは足りない。MMD Standard の Toon 寄せ合成や既存 project の保存値互換を失う可能性がある
- SQLite WASM を undo/redo の中核にすると、操作粒度や副作用分離の問題を DB で隠してしまう可能性がある。そのため、v0.2.0 では Action / Command / in-memory HistoryManager を先に評価する
- 高頻度入力ログを雑に SQLite へ流すと、描画や再生の負荷調査そのものに影響する可能性がある
- OBJ や点群読み込みは、MMD 本体機能ではなく scene object / accessory 寄りの扱いになる。タイムラインや材質 UI に混ぜると scope が膨らむ
- GLTF / GLB で詰まったように、Babylon 側で読み込めることと MMD_modoki の scene / WebGPU / WGSL / UI に統合できることは別問題
- 照明・アクセサリ・セルフ影・重力は babylon-mmd の外側で評価する `modoki-owned tracks` になりやすい。タイムライン UI に出すだけでなく、保存・再生時評価・undo/redo の責務を決める必要がある
- Action 管理を入れずに shortcut custom / gamepad / MIDI を増やすと、入力経路ごとの挙動差とテスト漏れが増える可能性がある
- Zustand に runtime object や大きな animation buffer を入れると、保存 / 読み込みや Babylon runtime との同期問題が増える
- Tailwind CSS を全面移行として始めると、見た目変更と実行経路変更が混ざり、回帰原因を切り分けにくい

## 次の判断

Babylon 9.2 + babylon-mmd 1.2 の実モデル確認と Worker 対応物理は一段落した。次は Frame Graph 標準描画パイプライン PoC を優先する。

Frame Graph は v0.2 の描画標準候補として扱い、まず DoF / Bloom / LUT / SSAO の順序を動かせる最小構成を作る。

ただし、MMD 材質・outline・透過・WebGL2 fallback が崩れる場合は、旧描画経路を退避経路として残す。

DoF は既存計測で重いケースが見えているが、Frame Graph 化で経路そのものを触る可能性が高いため、現行 LensRenderingPipeline だけの細かい最適化は後回しにする。

影は描画負荷への影響が大きい。既定の影描画範囲縮小とモデル単位の遮蔽影 OFF を入れたので、以後は必要に応じてプロジェクト単位の運用で逃がす。

既存の設計メモ:

- [physics-worker-implementation-plan.md](./physics-worker-implementation-plan.md)

Action / Command 管理は、v0.2.0 の編集基盤整理として優先度を上げる。まずは keyframe add / delete / 1f nudge を対象にし、button / shortcut / timeline 操作を同じ Action 経路へ寄せる。Action 単位の Vitest を増やし、in-memory HistoryManager + command diff で undo/redo の最小 PoC を作る。

Zustand は、UI / editor state の lightweight snapshot 用として検討する。selection、editing mode、dirty、`canUndo` / `canRedo` などに限定し、Babylon object、MMD model 実体、大きな animation buffer、project save format は入れない。

SQLite WASM は、v0.2.0 では undo/redo の中核にしない。DB を入れても undo/redo の本質である「1 操作の粒度」「逆操作」「副作用の整合」は消えないため、まずは既存の [undo-redo-investigation.md](./undo-redo-investigation.md) にある `HistoryManager + command + 最小差分` 方式を優先する。SQLite WASM は必要になった場合に、`input_event` / `command_event` / `error_event` の観測ログやクラッシュ復元の後続 PoC として扱う。

Tailwind CSS は、UI のガワ整理を進める段階で Action 化済み UI または設定画面から段階導入する。全面移行から始めず、相対値 / 絶対値の混在や似た component の散らばりを小さい範囲から整理する。

Electron / Vite major update は、Babylon / babylon-mmd 更新が一段落しているなら検証タイミングとして悪くない。ただし Frame Graph や Action / Zustand / Tailwind の実装と混ぜると切り分けが難しいため、別コミットで `vite@6.x + vitest@4.x` を先に確認し、通ったら `vite@8.x` へ進むか判断する。

## 2026-07-01 FrameGraph / PostFX 現行補足

このメモ内の FrameGraph 記述は、2026-04 から 2026-06 にかけての計画・判断が混ざっている。2026-07-01 時点では、FrameGraph は v0.2 の描画標準候補として、post effect stack を中心に実装が進んでいる。

現在の状態:

- MMD scene render 全体の置き換えではなく、既存 scene color を取り込む post effect backend。
- `frameGraphPostStack` で順序と enabled を保存する。
- 個別 ON/OFF はパラメーター値とは分離し、OFF にしても効果設定を保持する。
- `Offset Rim -> Bloom` のような順序効果は実機で確認済み。
- `Offset Shadow` / `Offset Rim` は実験的だが、MMD 向けスタイライズ効果として stack に入っている。
- Luminous は AutoLuminous 完全互換ではなく、材質 / luminous mask ベースの FrameGraph stack 効果として扱う。
- WebGPU FrameGraph の texture 依存は build 後に固定されるため、順序 / enabled 変更は live reconnect ではなく backend rebuild で扱う。

未解決として、rapid reorder / toggle の debounce、Offset Shadow / Rim の model mask、Offset Rim の thickness 品質、外部 LUT と PNG / WebM 出力反映の確認が残る。
