## 2026-08-30 モデル読込回帰の追加確認

- 対象: [V022-061](./v0.2-feedback.md#v022-061-v021以降でどのmmdモデルを読み込んでも暗転して終了する)
- 共有された報告: v0.2.0では読み込めるが、v0.2.1、v0.2.2、v0.2.3では読み込めない。modelを変更しても回避できず、どのmodelでも画面が真っ暗になった後にアプリが終了またはcrashするとの追加確認がある。
- 非再現状況: プロジェクト所有者のWindows環境では再現していない。環境依存の可能性はあるが、影響範囲の大きさからP0を維持する。
- 所有者判断: 個別assetの互換問題ではなくmodel読込経路全体を阻害する可能性があるP0回帰として、早期修正対象に採用する。
- 状態: `fix planned`。まず配布可能fixtureで再現し、最初の版境界であるv0.2.0とv0.2.1のA/Bから失敗段階を切り分ける。
- 履歴上の第一候補: v0.2.1へ入った`789e6af`のPOSIX file URL修正は時期が一致する。ただし通常のWindows drive pathでは修正前後のURL形が同等なので、UNC / network drive、特殊文字、実配置pathを確認するまで原因確定しない。同期間のphysics runtime初期化、shadow再同期、outline shader読込も競合候補として残す。
- 権限設定の履歴確認: v0.2.0からv0.2.1の間に、file IPC、BrowserWindowのsecurity設定、ASAR / Electron Fuses、permission handlerを変更した形跡はない。Windowsのfile access権限を明示的に厳しくした証拠はなく、権限変更説は現時点で支持されない。
- 環境差の仮説: OneDrive等の同期folder、UNC / network drive、外付けdrive、特殊文字path、OS ACL、security softwareは、path / URL解決やfile read失敗を権限問題のように見せる候補として残す。報告環境の情報がないため原因扱いはしない。
- 終了症状の仮説: 通常のfile read errorよりもrenderer / GPU processまたはnative runtimeの異常終了を疑う余地がある。通常起動でもprocess終了理由とmodel読込milestoneを記録できる診断を、再現確認と並行して検討する。
- 最短の報告環境確認: 同じmodel folderを`C:\MMD_test\model\`のような短いlocal ASCII pathへcopyし、v0.2.0 / v0.2.1をA/Bする。元配置区分、特殊文字の有無、GPU / backend、最後に到達した読込段階も同時に記録する。
- 判断分岐: 短いlocal pathで成功すればpath / URL / OS環境差を優先し、同じpathでもv0.2.1だけ失敗すればphysics runtime、shadow、shader、renderer / GPU process側を優先する。
- 不足情報: model形式、Windows version、GPU / driver / backend、modelとアプリの配置path、配置先の種類、読込停止段階、process終了理由、error log。
- 制約: 対象modelは明示的な利用許可なしに探索・読込しない。
- 物理経路の版境界確認: `loadPMX()`はv0.2.0時点からPMX parse前に`physicsInitializationPromise`を待ち、物理利用可能時は`createMmdModel(..., { buildPhysics: ... })`でmodel physicsを生成していた。待機や`buildPhysics`の存在自体はv0.2.1で新設されたものではない。
- v0.2.1で増えた物理処理: Bullet floor用のglobal静的剛体、model physics生成後のfollow-bone速度同期、damping / mass互換処理、constraint solver parameter適用、runtime bone評価順正規化が追加または大幅拡張された。互換補正UIがOFFでも、model physics初期化、follow-bone hook、damping参照、constraint parameter適用、bone評価順正規化は到達し得るため、物理仮説は初期化だけでなくmodel生成後処理まで分けて追う。
- 配布経路のbackend注意: v0.2.0 / v0.2.1の実装はpackaged buildでMPRを未採用とし、通常はBullet SPRへfallbackする。開発版のMPR成功だけでは配布版の再現確認にならない。
- 2026-08-30 local A/B: 同一Windows環境、WebGPU、配布可能な`dynamic-follower.pmx`（2剛体・1joint）でv0.2.0 / v0.2.1を自動model-load smokeした。開発既定のBullet MPRと、配布版相当として強制したBullet SPRの双方で両versionとも読込後のFrame Graph描画まで成功し、暗転・process終了は再現しなかった。
- A/Bの解釈: 少なくとも小型の剛体・joint付きfixtureでは、v0.2.1の物理変更だけで全環境に発生する回帰ではない。報告環境固有のCPU / GPU / driver / security software、実model規模、packaged ASAR、配置pathとの組合せが必要な可能性を残す。
- 次の最短切り分け: 報告環境向けにphysics runtime初期化と`buildPhysics`を完全に迂回する診断起動を用意し、同じmodel / pathで通常起動とA/Bする。迂回時だけ成功すれば、次にfloor、model physics生成、生成後補正を段階的に戻す。迂回しても終了するならpath / material / shader / GPU process側を優先する。

### 原因究明で得たもの

- DoFは`dofEnabledValue`とFrame Graph stack entryのenabledを別々に保持する。effect layer checkboxは`setFrameGraphPostEffectStackEntryEnabled("dof", active)`だけを呼び、project serializerは別側の`host.dofEnabled`を保存する。この片側更新がV022-060で再現したUI / runtime / 保存値不一致の直接原因である。暗転までの追加条件は、旧projectのeffect順、depth resource、backend snapshotが不足しており未確定。
- camera motionは、通常再生またはexport用`externalPlaybackSimulationEnabled`中は毎frame viewportへ適用される。一方、停止中の`seekTo()`はtimeline targetがcameraでない限りcameraを同期しない。同じframe番号でも「frame stepでは表示、再生 / WebMでは消失」という比較が異なるcamera poseになり得るため、V022-040 / 041はまず両経路のcamera position / target / up / FoVを同時記録する。報告motionなしにbounds defectと断定しない。
- V022-014の通常`mmd-standard`経路はPMXのspecular colorを`specularColor`、shininessを`specularPower`へ渡している。非表示のPBR互換経路はshininessを`roughness = shininess / 100`へ写すため、高shininessほど粗くなる方向でMMDの光沢感と逆転する原因候補がある。報告時pipelineが不明なので確定原因にはしない。
- V022-042でもPBR互換proxyは同じshininess / roughness対応を使い、sphere / toon texture morph channelは意図的に未対応である。ただし通常MMD Standardの報告modelを未使用のため、赤面黒化の直接原因とはまだ結び付けない。
- V022-053は現行standard physicsが常に1/60秒fixed stepで、30fps出力は概ね2 step/frame、60fpsは1 step/frameとなる。実時間1秒当たりのstep数は同じで、「60fpsで重力計算が倍」は原因にならない。硬さの比較には同一physics snapshot、同一backend、同一frameのrigid body / bone軌跡が必要。
- V022-004 / 061のpath経路は`encodeURI(file://...)`を使う。通常のspace / Unicodeはencodeされるが、URL予約文字を含む実path、UNC、同期folder、ACL / security softwareはfixtureで未検証である。現行fixture成功だけでは報告環境のpath / process終了条件を除外できない。

## 2026-08-30 v0.2.4 多言語データ・BVMD方針

- 所有者判断: 多言語翻訳強化をUI文言だけに限定せず、中国語系の漢字を含むUnicode名を
  そのまま読み込み・編集・保存できるtoolへ進める。
- BVMDの位置づけ: VMDのShift_JIS固定長制約を受けず、UTF-8可変長のbone / morph / IK名を
  保持できるため、多言語対応のmotion入出力形式として採用方向とする。
- 保存方針: project JSONとBVMDではUnicode名を保持する。従来VMDは互換出力として残すが、
  符号化不能・固定長超過・名前衝突を黙って置換または切り詰めない。
- 実装範囲: BVMD 3.0.xのmodel / camera motion読込と、編集中の`MmdAnimation`からの
  BVMD保存を一組で検討する。BPMXの採否、旧BVMD 2.x、変換専用UIは別判断とする。
- 完了確認: Shift_JISにない漢字、中国語・韓国語、15byteを超えるtrack名について、
  BVMD読込、timeline編集、project保存・再読込、BVMD再保存で無損失round-tripを確認する。
- 詳細: [BPMX / BVMD調査メモ](./bpmx-bvmd-babylon-mmd-support-research-2026-08-30.md)
