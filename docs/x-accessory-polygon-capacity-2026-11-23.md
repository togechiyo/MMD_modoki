# テキスト形式の X アクセサリで1,000万三角形を読み込む

2026-11-23、Windows の Electron で、静的な `.x` アクセサリを「ファイル → 開く」から読み込み、WebGPU と WebGL2 の両方で全1,000万三角形の描画を確認した。格子は2,500×2,000セル、共有頂点5,004,501個、単一材質。各セルを2枚の三角形に分け、重複面は含めていない。

| 描画モード | 形状データ | ファイル容量 | 対象欄に表示されるまで | アプリの使用メモリ合計（観測最大） |
| --- | --- | ---: | ---: | ---: |
| WebGPU | 位置・面・材質 | 342 MiB | 7.6秒 | 2.85 GiB |
| WebGPU | 上記にUV・法線・面ごとの法線インデックスを追加 | 722 MiB | 12.3秒／再測定11.9秒 | 3.26／3.32 GiB |
| WebGL2 | 位置・面・材質 | 342 MiB | 7.1秒 | 2.70 GiB |

各測定は独立した Electron で実行した。GPU は GeForce RTX 3070、ビューポートは1152×648。すべての測定でカメラの有効メッシュに32ビットのインデックス3,000万個があり、画面で赤い材質が45万画素以上を占めた。WebGPU 検証エラーは0件。属性付きファイルの再測定では、GPUに渡した法線とUVの先頭値も照合した。メモリは2秒間隔で各プロセスのワーキングセットを合算した値。材質数、テクスチャ容量、エフェクトの構成によって実機の負荷は変わる。

## ローダーの変更

以前はファイル全体の字句と面ごとの配列を作り、法線を持つ面は三角形の各頂点に展開していた。現在はローカルのファイルをバイト列で受け取り、1 MiBずつテキストに変換する。各面の開始位置と頂点番号を型付き配列に格納し、材質別の描画順にインデックスを一度だけ組み立てる。位置と法線の組み合わせが同じ頂点を共有し、法線が変わる境界は保持する。

逆向きの重複面は、三角形化前に材質・量子化した位置とUV・頂点の循環順を照合して取り除く。描画バッファがデバイスの上限を超える場合は三角形を複数のメッシュに分ける。[重複面の判定条件](./x-accessory-alpha-coplanar-rendering-note-2026-08-20.md)

## 複数の大型アクセサリを追加したときのクラッシュ

同日の Windows / WebGPU の実機ログでは、地形と樹木3件の読み込み完了後、4件のアクセサリに合計28,193,248頂点、14,380,154三角形があった。次の樹木の読み込み開始から13.747秒後、完了を記録する前に描画プロセスが終了した。追加直前の計測は43 FPSで、RC GI と Sky Ambient RC はともにオフだった。

各樹木メッシュは約800万頂点を保持し、描画に使うインデックスは約600万個だった。重複面除去後に残る未参照頂点と、次のファイルを展開する間の一時メモリが調査候補になる。今回のログに確保失敗の箇所や RAM・VRAM のピーク値はなく、メモリ不足は未確定。Windows の同時刻のイベントにも GPU リセットやシステムのメモリ枯渇の記録はなかった。

Electron が記録した終了コード `-36861`（`0xFFFF7003`）は、ダンプの取得を要求したプロセスが Crashpad のハンドラに登録されていなかった場合の値。元の例外を特定するには、ダンプまたは読み込み段階ごとの診断が必要になる。[Crashpad の終了コード定義](https://chromium.googlesource.com/crashpad/crashpad/+/c4cdec3d72a2d2abad84a98bc0bcf525333b3280/util/win/termination_codes.h)

## 未使用頂点を取り除いた後の累積読み込み

重複面を取り除いて三角形を組み立てた後、実際に参照する頂点だけを描画バッファに詰めるようにした。位置・法線・UVを同じ頂点番号で対応付け、UVや法線が分かれる境界と材質ごとの三角形の順序を保持する。

Windows / WebGPU で、838万三角形の合成地形を開き、同じ合成樹木を「ファイル → 開く」から4回追加して別々の位置に配置した。樹木は1本につき表裏の四角形100万組、入力800万頂点で、UVを持ち、法線は読み込み時に生成する。

| 追加したアクセサリ | 追加にかかった時間 | シーンの保持頂点 | シーンの三角形 |
| --- | ---: | ---: | ---: |
| 地形 | 6.48秒 | 4,194,304 | 8,380,418 |
| 木1本目 | 3.63秒 | 8,194,304 | 10,380,418 |
| 木2本目 | 3.73秒 | 12,194,304 | 12,380,418 |
| 木3本目 | 3.97秒 | 16,194,304 | 14,380,418 |
| 木4本目 | 3.52秒 | 20,194,304 | 16,380,418 |

木1本につき200万三角形を保ち、保持頂点は400万個になった。木4本で省いた位置・法線・UVは計1,600万頂点分、属性配列1組あたり約488 MiBに相当する。読み込み中に1秒間隔で観測したアプリ全プロセスのワーキングセット合計は最大3.15 GiB。1152×648の画面で5個すべての独立した形状が描画対象に入り、地形と樹木の色が表示され、WebGPU検証エラーは0件だった。元のクラッシュに使われた個人モデルは今回の試験に含めていない。

静的な `.x` ではカメラ外のメッシュを描画対象から外す。Babylon.jsの標準の判定で境界球と境界ボックスを使い、地形のように横長の形状にも対応する。影を落とすメッシュは別に管理する。WebGPU・WebGL2それぞれのClassicとFrameGraphで、画面外に出た箱が床に落とす影と、カメラを戻したときの再表示を確認した。床中央の平均輝度は、4通りとも影ありで182.0、箱の影をオフにすると226.3だった。 [Babylon.js のカリング方式](https://doc.babylonjs.com/features/featuresDeepDive/scene/optimize_your_scene/#changing-mesh-culling-strategy)

## 元のモデルでの実機再確認

同日、ユーザーが元の地形と樹木で再試験し、以前クラッシュした4本目の読み込みが完了した。Windows / WebGPU（FrameGraph）の実機ログでも、18:53:29.932に読み込みを開始し、18:53:40.021に完了した（10.089秒）。直後の地形＋樹木4本は合計20,194,304頂点・16,380,418三角形で、合成試験と同じ規模に達した。
